# 拾光 MCP 委托

## 触发与授权

- 用户明确要求利用拾光完成具体任务：直接执行已授权范围，不重复询问是否使用拾光。
- 用户未点名拾光，但任务需要登录用户账号或操作已登录网页：先询问“这个任务需要操作你账号登录的网页，是否利用拾光完成？”得到明确同意前不调用拾光，也不绕过该选择使用其他浏览器工具。等待时继续不依赖账号的工作。
- 同一任务已有授权则继续；用户拒绝不调用，沉默不视为同意。公开网页检索、普通本地开发不触发上述询问。讨论或修改拾光技能不代表授权新建外部操作委托。
- 使用拾光不扩大任务范围。把已有许可和仍需用户确认的边界明确传给拾光；委托方审核关键节点不代表新增用户授权。

## 接口发现

先查看实际工具目录和参数，不猜接口。Codex 工具名通常为 `mcp__shiguang__<接口名>`，Cursor 按实际目录匹配。

| 接口 | 参数 | 用途 |
| --- | --- | --- |
| delegate_to_shiguang | goal、origin、title | 为新目标创建任务 |
| wait_shiguang_delegation | id、timeout_seconds | 挂起等待关键节点、问题或结果 |
| reply_shiguang_delegation | id、content | 回答、审核关键节点、纠偏或补充事实 |
| resume_shiguang_delegation | id、content（可选） | 继续暂停或出错的原任务，保留历史 |
| get_shiguang_delegation | id | 必要时读取完整交流记录 |
| list_shiguang_delegations | 按实际 schema | 找回原任务，避免重复委托 |
| cancel_shiguang_delegation | id | 中断指定任务 |

旧版本没有 resume 时用 reply 对原 ID 传明确续跑意见。没有 report_checkpoint 时在目标中要求拾光在关键节点用 ask_peer 回传并暂停。工具未连接就说明缺失，不伪造执行。

## 精准下达任务

委托方负责项目理解、源码分析、任务拆分和最终验收；拾光负责在限定范围内自主执行。先补齐自己能查明的信息，再下达可独立执行的任务，不能把“去弄好这个项目”当作目标。

在 goal 中写清以下信息，按任务需要取舍，不机械堆模板：

- **目标和完成标准**：具体对象、实际要完成的动作、可核验结果，区分检查、修改和发布。
- **执行环境**：准确网址、账号内属性/项目名、分支/提交、页面路径、日期/国家/设备等必要过滤条件；本地与生产必须分清。
- **必要上下文**：已完成事项、真实已知事实、当前限制，以及已有报告或数据的绝对路径。相对产出路径先由委托方解析，不能让拾光遍历磁盘找仓库。
- **允许和排除范围**：允许的操作、可读取的文件/目录、输出位置、不得触碰的对象；未明确委托源码任务时，明确“不要搜项目源码、读取项目配置或全盘找文件；缺少项目事实、路径或材料先 ask_peer 向委托方询问”。本任务的临时证据、下载和指定归档可以读写。
- **关键节点**：约定少量会影响执行方向、外部结果或验收的阶段，写清何时回传、验收依据和下一阶段。每个节点要求 report_checkpoint 回传并暂停，委托方回复后再继续。简单只读查询可直接交付结果，不强加流程节点。
- **停止和回传条件**：对象不符、前提不成立、需要越界或原方法持续失败时停下来问，不自行扩大搜索、修项目或换目标。

不要传密码、令牌、Cookie 或无关私有材料。授权已覆盖的操作明确说明，仍需用户确认的动作保留给用户。

例如浏览器验收：给精确本地 URL、检查项、报告绝对路径；约定“确认版本与测试对象后回传一次；完成核心用例并有截图后回传一次；得到审核再做剩余检查”。若对象已明确且测试简单，只保留核心结果节点。每次回传写节点、已完成结果、对应证据、偏差/阻碍和下一步，避免只说“进度正常”。

## 关键节点把控与纠偏

1. 创建后保存真实 ID，后续始终复用。丢失 ID 先 list/get 核实；创建返回不确定时先查询，不重复提交。
2. 用 wait 挂起等待，每次通常 30–60 秒。running 超时代表还在执行；可继续等待或完成独立工作。不要逐次 get 完整历史、查看每次工具调用或实时盯屏，也不要因常规等待反复插话。
3. waiting_peer 时区分上下文问题和关键节点回传。checkpoint 字段或 question 应包含节点、结果、证据和下一步。委托方对照原目标检查：对象/环境是否正确、证据是否覆盖该节点、动作是否越界、下一步是否符合约定。
4. 符合预期：用 reply 明确审核结论和下一阶段允许范围，让拾光自主完成该阶段。结果缺证据就请求节点所需证据，不要求逐次汇报工具过程。
5. 发现跑偏：立即用原 ID 的 reply 纠正，写“停止哪个偏离动作；保留哪些已完成结果；正确对象/事实/路径；只做什么；下一节点何时回传”。先提供自己掌握的项目上下文，不让拾光自行补全源码分析。对方已在节点暂停时回复即继续；若实际仍在执行且继续会产生越界影响，用 reply 插话中断本轮并修正，不另起任务。取消用于用户要求终止或确实无法安全继续的任务。
6. waiting_user 时由用户在拾光窗口回答；不得代答或绕过。普通节点审核由委托方自行处理，无需逐次询问用户。
7. blocked/error 时检查真实原因和已完成结果，在原 ID 上 resume/reply。步骤耗尽可继续；清单超过12项、单项超过80字等错误要求缩短/合并或暂不使用清单，不将它当成目标失败。外部动作结果不确定时先核实，不能直接重复写入/发布。相同真实阻碍不无限续跑，补齐条件或请求用户所需信息。
8. 最终逐项核对完成标准与证据，报告完成、未完成和局限。complete 标签本身不能代替验收；失败/暂停/取消不报告为完成。缺项用原 ID 补充纠正，只有新目标才新建委托。

长时间执行向用户简要说明实际状态；关键节点用于方向与结果把控，阶段内部由拾光独立处理，不把委托退化为遥控每一次操作。

## 触发示例

- “利用拾光查看我的 Search Console 数据”：直接委托准确属性、时间与只读边界，必要节点核实过滤和核心证据。
- “打开我的网站后台，检查登录后的设置”：先询问是否利用拾光，同意后委托。
- “搜索公开资料”：正常公开检索，不触发拾光。
